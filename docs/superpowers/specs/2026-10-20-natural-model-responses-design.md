# 自然语言模型回复设计

## 目标

让在线模式下的训练计划说明、营养目标与具体餐单、每日建议更贴合用户当前情况并以自然语言表达。模型负责综合已确认档案、反馈、趋势、本地知识结果和工具结果，自行规划、组织、表达并在同一次生成中自检。演示模式继续使用本地规则，不调用外部模型。

## 范围

- 在线计划：模型可以自然地改写计划摘要，解释安排与用户目标、时间和条件的关系。
- 在线饮食规划：`NutritionPlannerAgent` 调用模型，根据档案、目标、训练安排、预算、食物来源、过敏/不耐受和当天饮食条件，制定营养目标和具体餐单。模型负责判断目标与安排，不只是润色本地生成的菜单。
- 在线建议：模型可以综合本次反馈、历史趋势、检索结果和局部调整预览，自行组织完整回应，不再局限于逐字段润色固定句子。
- 每日建议的前端呈现改为优先显示一段连贯、自然的回复；如模型返回清晰的行动要点，可一并显示，但不要求用户看到 JSON 或字段术语。
- 模型在单次生成提示中自检是否答非所问、遗漏明确条件、内部矛盾或使用生硬模板，并直接修订后输出。暂不增加第二次模型审阅调用。

## 不在范围内

- 反馈事实抽取继续使用结构化字段和确定性事实校验；不得让自然语言回答替代事实记录。
- Demo 模式和 provider 不可用时，热量、三大营养素及餐项估算可使用 `NutritionPlannerAgent` 的本地估算与模板回退；在线模式的主规划结果由模型生成。
- 模型不能直接执行写操作、确认反馈、确认计划或确认训练调整。
- 不重做 RAG 检索、训练动作规划、长期记忆或数据库结构。

## 设计

### 模型输入与职责

Live advice 输入包括已确认档案、本次已确认反馈、本地规则和健康提示、当前适用计划、趋势、相似历史、知识检索结果及局部训练调整预览。Live plan 输入包括已保存档案、目标日期、训练可用条件、本地训练计划、baseline 策略上下文，以及饮食规划器可用的营养估算工具结果。`NutritionPlannerAgent` 的 Live 输入还包括目标、饮食档案、训练/休息日、预算和餐食来源；单餐重规划额外包含已确认反馈、可获得或想吃的食物、已吃内容和本餐预算。用户内容和检索到的创作者文本明确标记为不可信资料，仅供判断，不是指令。

模型可自行选择回答重点、安排信息顺序、解释建议理由，并使用自然中文直接回应用户。自然度提示鼓励简洁、具体、友好、不说教；避免固定模板和机械重复。不要求对用户展示“综合分析”等内部过程。

模型面向用户的建议使用自然语言，不要求 summary/suggestions JSON；工具调用阶段仍按 OpenAI-compatible 工具协议工作。`AdviceData` 增加可选的 `response` 文本字段供新 live 回答和前端使用，旧 `summary`、`suggestions` 保留以兼容历史记录和 API 消费者。Live 模型生成成功时，前端优先显示 `response`；本地回退和旧记录继续显示现有 summary 与 suggestions。计划说明仍更新 summary。饮食规划模型通过受约束的结构化接口返回营养目标、餐次、食物与份量、估算营养和费用、替换建议及待确认问题；结构化是程序和界面的数据契约，不意味着把 JSON 展示给用户。模型负责这些内容的规划，本地估算仅供参考/回退，不得静默覆盖有效的模型结果。

### 验证与安全

模型自检是内容质量步骤，不视为可靠安全屏障。程序保留少量确定性硬约束：

- 异常症状触发时，跳过模型并保留暂停训练/就医提示。
- 已记录过敏原不得被模型作为可食用选项推荐；遇到输入或输出明确冲突时，以档案限制为准。
- 营养规划结果经过 Pydantic 字段范围及一致性校验；本地校验拒绝违反已知过敏/不耐受、预算边界或必要输出结构的结果。校验不能证明营养建议医学上适合个人，也不把公式估算误称为精确需求。
- 不输出诊断、治疗指令或停药建议；营养目标属于基于档案信息和明确假设的估算，不能宣称为精确测量或医疗处方。
- 营养数值、补剂剂量、训练处方和来源 ID 等结构化字段保持不可由文案覆盖。
- Advice 模型输出或 provider 不可用时，保留现有确定性本地建议；营养规划模型输出或 provider 不可用时，使用明确标注为估算的本地目标和模板餐单，并记录安全、解析或 provider 回退状态。发生过敏冲突时不得回退为含冲突食材的模板，应返回安全问题或不含具体食材的结果。

移除当前对所有改写文本的统一严格数字/来源 grounding 限制，改为检查真正的硬约束和回复字段边界。模型可以用自然语言引用输入已有的数值和知识，也可以给出营养估算，但需要说明重要假设；不得捏造用户档案数据或覆盖明确限制。

### 错误处理与兼容性

- Provider timeout 或无效响应时回退到本地生成内容，不丢失已确认反馈或知识快照；如果模型营养规划违反过敏硬约束，则拒绝冲突结果并返回无冲突安全回退或要求澄清。
- 现有 AdviceData、PlanData 持久化字段继续可读；新增 `response` 可选字段，无需迁移 SQLite。
- 旧计划、旧建议和导出格式继续工作。
- trace 继续保存 provider 状态、调用次数、token 用量、工具调用和知识快照 ID；可增加有限的输出验证状态，不保存不必要的完整 prompt。

## 验收标准

1. Demo 模式不调用 provider，输出保持确定性。
2. Live advice 的模型能把档案、反馈和至少一个适用工具结果综合为连贯自然的中文，而非只改写固定模板。
3. Live plan 允许模型自然解释训练安排；训练动作仍由现有训练规划路径负责，饮食规划子 Agent 调用模型制定营养目标和具体餐单。本地硬约束和数据校验仍生效。
4. 不可信用户文字或知识卡中的指令不会变成 agent 指令。
5. 异常症状仍跳过模型；硬约束冲突时阻止或回退，不依赖模型自检通过。
6. Provider 故障时回退正常，现有工具追踪和 token 统计保持正确。
7. 前端优先显示自然语言 `response`、不显示 JSON 包装，旧数据仍可展示；建议文字在桌面和窄屏不溢出。
8. 测试覆盖自然输出、拒绝新增个体事实、过敏冲突、急症跳过、provider 回退及旧记录兼容。

## 主要权衡

这是“单一主 Agent 编排，饮食规划模块调用模型，程序兜底少量硬约束”的设计。模型负责综合需求和规划具体饮食内容，程序负责接口契约、已知过敏限制和失败回退；本地公式估算不再充当在线营养计划的唯一或主要结果。结果一致性会更依赖模型质量，回退路径可能更简短、模板化。保留单次生成内的自检，避免额外模型调用带来的 token 和延迟，同时不把自检当作独立安全验证。
