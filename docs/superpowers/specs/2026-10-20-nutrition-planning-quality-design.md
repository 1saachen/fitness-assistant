# 饮食规划质量与反馈校准设计

## 目标

让增肌、减脂和维持目标的餐单更容易执行，并用用户持续记录的体重与饮食执行情况提出有依据的复盘建议。保留现有本地目标估算、过敏限制和用户确认长期档案的安全边界。

## 范围

- 生成餐单时综合训练目标、体重/身高/年龄、活动水平、训练频率、食物过敏与不耐受、长期偏好、餐食来源、预算和当天可用/想吃/已吃食物。
- 餐食建议需包含可理解的食物、份量和替换方式；呈现份量时标明生重/熟重或份数，并使份量与热量、蛋白质、脂肪、碳水估算保持合理一致。
- 缺失过敏或不耐受状态时，不对具体食物作安全承诺并提出澄清问题。其他缺失项优先采用保守假设并清楚说明；只有无法安全或有效地继续规划时才阻断并追问。
- 使用至少14天的体重及饮食执行记录判断是否需要复盘。样本不足、执行信息缺失或趋势不稳定时不建议调整热量。
- 调整只作为长期计划复盘建议呈现。用户重新确认长期计划前，不改变已确认的每日热量和宏量目标。

## 饮食规划行为

本地确定性计算继续负责热量与宏量营养素的起始目标、范围校验和已知限制保护。餐单生成需遵循目标方向：减脂从温和缺口开始并尽量保留训练表现；增肌从小幅盈余开始，避免不必要的快速增重；维持目标保持估算维持摄入。所有目标均标为估算起点，不作为医疗处方。

餐食须优先适配已知餐食来源和预算。用户提供当天食材时，优先使用可用食材；“想吃”与“可用”冲突时说明取舍，不把愿望当作库存事实。已吃食物仅用于规划剩余餐次，不用补偿性节食抵消。食堂、外卖的油量、份量和价格不确定时保留估算说明。训练日可安排餐次时机，休息日保持长期目标，不因漏练下调热量。

## 反馈校准

基于截至规划日的最近14至28天反馈，比较前后两个至少7天的体重均值，并使用明确记录的饮食执行状态作解释。只有存在足够体重样本（窗口至少4次有效称重）且有可判断的执行记录时，才形成方向性建议。单日体重、单条饮食记录、漏练或摄入估算不单独触发热量变化。

若减脂期间体重趋势长期未下降且饮食执行稳定，可建议检查记录/份量；由于当前反馈没有结构化饥饿感和训练表现字段，缺少这些信息时不贸然减少热量。若下降过快且反复记录到疲劳，可建议小幅增加摄入并复核恢复。增肌期间体重长期不升且执行稳定，可建议小幅增加摄入；若增重明显过快，可建议小幅回调。任何建议需包含观察到的证据、建议复核周期和不确定性，不输出虚假精确的趋势结论。

建议以约100至200 kcal/日的小步幅为上限起点，且每次调整后至少再观察约两周。无可靠样本、执行度低或饥饿/疲劳/表现相互矛盾时，提出补充记录或先维持目标，不给出热量调整结论。已知疾病、孕产、异常症状或饮食失调风险触发既有健康护栏，不提供个体治疗方案。

## 数据流与展示

复用已确认的反馈字段 `weight_kg`、`diet_followed_plan`、`intake_kcal`、`food_summary`、`fatigue` 和 `training_completed`，以及已有14天趋势摘要。新增的营养复盘建议写入当天计划的建议区域与可追溯依据，不修改历史反馈、不自动覆盖长期目标。餐单中的用户文本继续以纯文本安全渲染。

## 验收

- 增肌、减脂和维持目标均能生成餐单，份量、替换、预算及估算说明符合档案与当天条件。
- 未知过敏、明确过敏、素食/纯素、低预算、食堂/自炊/外卖、已吃食物和休息日路径均有针对性测试。
- 不足14天、少于4次称重、缺失执行记录、单日波动和漏练均不会触发自动热量调整建议。
- 有连续且执行稳定的趋势时，系统给出保守、可解释的复盘建议；它不会改变已确认长期目标。
- 完成全量 Python 测试、相关前端测试、Ruff 和 `git diff --check`。
