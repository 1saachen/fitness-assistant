# 模型主导的健身 Agent 与 Harness

日期：2026-10-20

状态：用户已确认模型负责主要规划、工程提供 harness 的方向。根据用户要求，重新核对当前训练子 Agent、饮食模块和主入口后修订本文：保留现有职责划分，逐步升级模型规划能力；单 Agent 保留为对照基线。此迁移路线供书面审阅，不代表目标能力已实现。

## 1. 目标与范围

系统根据用户目标、已确认档案、执行历史和当天条件，通过模型与工具的循环生成、核验和修订训练与饮食联合方案。模型拥有业务规划决策权；harness 提供事实、计算、执行边界和持久化。

目标范围为长期计划草案、当天联合方案、信息不足时的追问，以及确认反馈后的重新评估。沿用 `FitnessAgent`、`DailyPlanningService`、`TrainingPlannerAgent` 和 `NutritionPlannerAgent` 的现有职责边界，分阶段把业务规划交给模型。保持现有长期计划、当天计划、反馈和确认入口，避免同时重做界面、数据库和知识库。

训练和饮食模块已经存在，无需先撤销它们再实现单体规划器。第一阶段升级训练模块的模型规划和共用运行循环；第二阶段升级饮食模块并形成联合草案；第三阶段加入主 Agent 的按需委派与冲突修订。单 Agent 对照使用相同工具、约束和评估案例，作为后续评估配置，不作为改造现有模块的前置工程。各阶段可独立验收；不扩展通用工作流平台、向量数据库或后台定时服务。

## 2. 当前实现与待补能力

以下依据当前工作区源码和测试定义整理，包含尚未提交的文件；文档更新不等于重新执行了这些测试。

| 部分 | 当前已实现 | 仍需升级 |
| --- | --- | --- |
| `FitnessAgent` | 提供长期/当天计划生命周期入口，把生成与确认等操作交给 `DailyPlanningService`；建议模型可读取当前长期/当天计划 | 生命周期转发尚不是模型自主委派；旧建议路径仍先生成规则 baseline，再让模型改写 |
| `DailyPlanningService` | 实例化两个规划模块；重建训练进度、合并反馈、管理条件时间、限制解除记录、已执行项目及版本；把训练结果传给饮食模块 | 当前调用顺序由程序固定，缺少主模型识别冲突并要求子 Agent 修订的过程；长期生成即使传入 live 也没有模型规划调用 |
| `TrainingPlannerAgent` | `build_cycle()` 生成可配置循环；`plan_day()` 处理完成待定、顺延、跳过、睡眠与疲劳、持续伤痛限制、解除与再次报告；可注入 provider，部分 live 情况会调用模型 | 循环、动作、组次主要由本地规则生成；`_model_decision()` 仅接收当前描述、baseline action 和允许动作，不接收完整档案、历史及知识，也不提供工具循环；模型不能生成训练内容 |
| `NutritionPlannerAgent` | 生成目标及餐单，接收当天条件、已吃内容、长期目标和训练结果；休息日会调整加餐文案 | 当前完全本地生成；训练输入只形成有限适配，尚未实现模型规划和向训练端反馈执行冲突 |
| 状态与工具 | `PlanRepository`、`merge_feedback_days()` 和 `LocalTools` 提供版本、非空事实合并、只读计划上下文和预览 | 需要明确事实时间、状态与模型提议的边界，并补充模型可按需查询的工具和候选校验 |

现有训练子 Agent 有实际状态处理和集成价值，应保留这些成果。当前更准确的描述是“主入口协调两个专业模块，训练模块带有限模型判断”，尚不能据此声称训练与饮食均由模型自主规划协作。

本文在后续实施范围内取代以下旧设计约束：模型只能改写摘要、不能提出训练组次、营养模板是在线主结果、训练模型只输出 action。旧文档仍保留历史背景；实施时同步更新 README、API 文档和相关计划，避免两套约束并存。

## 3. 职责边界

| 能力 | 模型决策 | Harness 支持 |
| --- | --- | --- |
| 理解需求 | 识别意图、信息缺口、追问和假设 | 提供原始输入、确认事实与字段语义 |
| 长期计划 | 选择训练结构、起始营养策略、复盘条件 | 查询资料、计算参考值、管理草案与版本 |
| 当天训练 | 选择动作、组次、休息及顺延或恢复方案 | 提供动作元数据，核验器械、时间和明确限制 |
| 当天饮食 | 选择食物、份量、餐次和替换方案 | 查询营养、核算宏量与预算、报告数据缺口 |
| 知识使用 | 决定检索主题，判断适用性 | 执行受限查询，返回审核状态和来源 |
| 连续反馈 | 综合趋势提出调整和理由 | 精确查询、统计、保留已执行内容和历史 |
| 写入 | 产出提议与待确认候选 | 校验、确认、事务、版本检查与审计 |

计算公式和动作库是可调用工具，不能偷偷变成唯一允许的业务答案。模型可以根据工具参考结果提出不同方案，但必须明确假设并通过适用的约束校验。

## 4. 共用运行循环与职责路由

共用运行器负责模型调用、工具执行、校验修订与预算；训练和饮食模块各自提供角色上下文、工具权限及候选输出契约。复用同一运行器不表示共享同一段对话，也不表示所有任务必须调用多个模型。

第一阶段沿用现有主入口到训练模块的调用关系，将训练候选交付后续消费；第二阶段让饮食模块接收训练候选并输出饮食候选，组合后做联合校验。前两阶段仍是应用编排，不宣称已经实现主模型自主委派。第三阶段才由主模型决定委派及修订顺序，运行契约和工具可以直接复用。

每次专业规划遵循以下过程：

1. 应用建立本次任务，包含任务类型、目标日期、用户请求、档案与计划版本、当前执行事实和明确限制。必要事实由 harness 注入；模型按需继续查询。
2. 模型决定查询哪些历史、知识、动作和营养信息，工具返回结构化数据及可用状态。无需为所有任务预先执行同一组工具。
3. 模型返回待澄清问题或完整候选草案。
4. 候选草案进入统一校验；字段、计算或约束错误作为带路径和原因的结果交回模型。
5. 模型修订并重新提交。专业候选通过本地校验后交回调用者，不直接写入正式计划。联合草案通过统一校验后，由应用保存并展示自然语言说明与训练、餐食内容。
6. 按既有产品语义确认和启用。长期策略变更仍形成待确认新版本；当天更新可在既有授权范围内保存新修订，不自动覆盖已执行内容。

运行结果明确区分 `draft_ready`、`needs_input` 和 `failed`。前者表示结构化草案已通过本地校验，不表示已经由用户确认；后两者不能保存成可执行的完整方案。

所有模型响应、工具调用和修订都计入同一根任务预算，包括主 Agent、专业 Agent 和重试。初始配置为最多 12 次模型调用、20 次工具执行，每个专业候选或联合候选最多 2 次修订，根任务总时限 180 秒；保留供应商单次超时配置，子运行超时不得超过根任务剩余时间。预算可配置，达到任一上限即终止相关运行并返回明确原因。

## 5. 输入、输出与工具契约

### 输入与上下文

每次运行绑定 `run_id`、任务类型、日期、档案版本、长期计划版本及相关反馈版本。历史查询严格限定到任务日期，避免把未来记录用于过去规划。修订与后续追问必须绑定本次任务和版本；新增回答作为用户提供的补充条件，不自动升级成长期档案事实。

专业调用另带 `parent_run_id`、角色、候选版本和共享快照标识。限制事件保留来源、发生/报告时间、字段修订时间及解除时间，沿用当前对原始描述与结构化事实的区分，避免写建议或编辑无关字段使旧伤重新生效。

用户请求用于表达目标与偏好；引用知识和历史原文属于资料。它们都不能授予工具权限、跳过确认或改变系统约束。

### 模型输出

使用结构化接口交付业务结果，界面展示自然语言和可读计划：

- 公共字段：状态、说明、假设、待确认问题、使用过的来源引用。
- 长期草案：阶段目标、训练循环及动作参数、营养目标、恢复与复盘策略。
- 当天草案：训练或恢复决定、具体动作、餐次及食物份量、营养估算、预算、替换方案和修改理由。
- 信息不足：具体问题、缺失字段及受影响部分。无法核验的部分不声明已满足约束。

通过新增适配层把候选结果映射到现有计划数据结构。不得仅更新 summary 而丢弃模型生成的有效动作或餐单。工具返回的事实、已执行记录和来源 ID 不由模型自由改写。

训练候选保留现有 `action`、`training`、`restrictions`、`reasons`、`questions` 的语义，扩展完整训练内容、训练时段和负荷说明。`cycle_index`、`next_cycle_index` 由应用基于事件核验和派生，模型不得把未来安排标成已完成；策略性重排以明确修订提议表达。饮食候选保留目标和餐次结构，并增加消费的训练候选版本、已吃餐次、估算依据和冲突。子 Agent 的 `draft_ready` 只代表本专业候选就绪，不等于联合草案已通过。

### 工具

| 工具组 | 输入 | 输出与边界 |
| --- | --- | --- |
| 档案与计划 | 日期、受限查询参数 | 已确认事实、版本、当前适用计划及已执行部分 |
| 历史与趋势 | 日期范围、指标 | 精确记录与统计，缺失值和样本数 |
| 知识检索 | 查询、主题、返回条数 | 审核通过的内容、来源、适用条件；允许无匹配 |
| 动作查询 | 器械、动作或训练需求 | 已知动作 ID、器械、时间估算和可靠限制元数据 |
| 营养参考 | 有来源的身体参数、明确估算假设 | 公式参考值、方法和不确定性 |
| 食物与费用 | 食物、份量、单位、已知价格 | 营养与费用合计、来源、缺项和估算标记 |
| 候选校验 | 类型和候选草案 | 字段错误、约束冲突、可核验项及未核验项 |

不依赖外部食物平台才能完成首个闭环。先提供小型带出处的本地食物数据；未知食物或价格返回缺失，允许模型请求补充、改用可查替代项或明确保留估算。预算缺乏价格依据时不能显示为“已满足”。

运行时使用白名单、严格参数校验和结果大小上限。模型没有原始 SQL、任意文件访问或直接确认写入工具。候选校验既可由模型调用，也必须在最终输出保存前由 harness 强制执行。

## 6. 校验负责什么

保留确定性检查：

- 输出契约、单位、数值范围、宏量与热量计算的一致性。
- 动作与器械匹配、时间估算及已确认的明确活动限制；未知的限制兼容性应返回未核验或待澄清，不能冒充安全通过。
- 已知过敏和明确饮食限制；未知配料不能证明食物安全。
- 有数据依据的预算检查、来源 ID 存在性、历史查询日期范围。
- 已完成训练、已吃餐次、档案事实和用户确认边界。

不再用“模型必须等于规则 baseline”验证业务质量，也不把所有训练组次和营养数字都视为禁止输出。数值规划属于模型职责，事实测量和精确核算必须有依据。

健康异常处理保留现有必要停止提示；更细的伤痛适用性不能靠有限关键词或关节标签宣称已可靠判断。知识不足、限制不明时，模型应追问或停止受影响的规划。

结构校验和模型自检均不能证明训练或营养方案的专业质量，质量需单独评估。

## 7. 状态、写入和失败

- 保留 SQLite、档案和反馈确认、长期/当天计划版本、输入指纹和并发保护。
- 训练实际完成、明确跳过及已吃餐次属于可追踪事实。模型可以提议如何顺延、调整结构或复盘；程序根据已确认事件维护执行状态，不把提议当成已执行。
- 持续限制、显式解除及再次报告的审计语义继续保留；普通疲劳恢复与伤痛解除分开处理，清空当天条件不能解除持续限制。保留现有相关回归场景，但不把“睡眠低于某值必减一组”等业务启发式固定为 live 模型唯一答案。
- 当天决策不能无确认地改变长期目标；需要改变时生成长期修订建议。
- Provider 不可用、输出修订失败或预算用尽时，保留已确认数据与原有计划，并返回失败原因和重试入口。旧计划如需展示，标明尚未按本次条件更新。
- Demo 继续使用确定性样例，并标记为 `demo`；live 不静默回退到模板，不将模板结果计为模型规划成功。必要的固定健康停止提示可以单独显示。
- 第一阶段 live 追问通过补充 conditions 和预期快照 token 建立新的运行 ID；版本变化返回冲突，不恢复未持久化的模型对话。后续如实现持久化会话，再设计运行恢复机制。

轨迹保存模式、执行来源、模型与工具调用数、工具名及状态、来源快照、校验与修订结果、输入版本、耗时及供应商实际 token 用量。分别记录主入口、训练和饮食的运行 ID、provider 状态和消费的候选版本；根任务汇总去重后的实际用量，不能沿用“当天 trace 的 provider 只代表训练”的形式来声称两个 Agent 都成功。不额外保存隐式推理，不在普通日志记录完整敏感档案和密钥，不在缺少价格依据时估算模型调用成本。

## 9. 验收与评估

工程测试使用受控 provider 响应，证明循环、数据与边界；真实模型评估独立运行并报告供应商、模型、时间、失败和用量，不能由 mock 测试替代。

必须覆盖以下场景：

1. 相同档案下，模型可输出不同于固定模板的有效训练动作、组次与餐单，保存和展示保留其结构化结果。
2. “今天很累、只有20分钟、晚餐只能吃食堂”：模型查询必要历史后生成联合方案，核验时间、可用食物和预算；缺信息时追问。
3. 候选方案违反器械或营养计算约束时，返回具体错误，模型在预算内修订；程序不静默替换成 baseline。
4. 过敏信息不完整、食物价格未知、知识无匹配或历史不足时，输出正确的不确定性，必要时为 `needs_input`。
5. 重复生成不推进未完成训练；已吃餐次和已完成训练在修订中保留。
6. Provider 超时、非法工具、步数用尽、无效候选及版本冲突有明确失败状态，不破坏原有记录。
7. 单日反馈可触发复盘提议，但不能自动确认长期策略变更。
8. Demo 不调用外部模型；live 成功必须有真实或测试替身的模型运行证据，失败不能标记为成功。
9. 训练候选可追踪地传给饮食模块；休息日、已完成训练和已吃餐次均按实际事实处理。候选版本变化后，受影响的饮食候选重新评估，不能拼接不同快照的结果。
10. 保留并扩展 `tests/test_training_agent.py`、`tests/test_daily_plans.py`、`tests/test_daily_agent_context.py` 中状态与生命周期场景，覆盖同日饮食反馈不清除疲劳/伤痛、明确疲劳恢复、逐部位解除、再次报告、只读预览和长期版本优先。旧规则处方与 fallback 的测试限定为 demo 或明确的旧路径，新 live 测试按模型候选和明确失败语义验收。

评估报告区分可执行方案率、明确约束满足率、修订成功率、追问适当性、引用支持度、训练饮食协调质量、延迟与 token。结构与数值项尽量自动核验，专业合理性和可执行性进行人工复核；不以预设模板文本匹配作为质量标准。真实模型评估使用合成档案，避免默认发送用户真实记录。

## 10. 分阶段升级与协作评估

### 第一阶段：训练子 Agent 的完整模型规划

复用当前 `TrainingPlannerAgent`，建立共用运行循环、工具和候选校验。模型读取档案、历史、限制及长期目标后生成长期训练循环或当天完整训练内容；不再只选择 action。保留应用对实际完成、跳过、限制解除和版本的管理。饮食暂沿用当前路径并明确标记为规则来源，联合输出处于过渡状态，不能标成全模型协作。

### 第二阶段：饮食子 Agent 与联合校验

复用 `NutritionPlannerAgent` 并接入共用运行器。训练候选提供训练状态、时间、负荷说明、恢复需求和不确定性；饮食模块结合它及预算、已吃内容和供应条件制定候选，返回所消费的训练候选版本与无法满足的条件。单餐请求可直接调用饮食模块，无需为了形式完整再生成训练。

应用先按现有顺序组织两个专业运行，并强制核验联合草案。出现跨专业冲突时返回结构化冲突和受影响候选，尚未具备主模型协商时返回待处理状态；不能由程序擅自增加训练或削减餐食来凑结果。任一必要专业运行失败时，不保存成完整联合计划。

### 第三阶段：主 Agent 按需委派与冲突修订

主模型根据任务选择 `plan_training`、`plan_nutrition`，以候选版本与结构化冲突请求相应专业 Agent 修订，并解释最终取舍。例如训练推迟到晚餐之后，饮食模块需重新评估餐次；食物供应无法支持原安排时，饮食模块返回缺口，由主 Agent 结合用户目标请求调整或澄清，不能直接改写训练。子 Agent 不直接写正式记录，也不递归委派；共享根任务预算、事实版本和统一校验。

每个专业 Agent 必须有独立模型运行上下文、明确输入输出及工具权限。主 Agent 可以编排同一供应商/模型的多个角色；不要求不同模型，也不预设并行。存在训练候选依赖时按顺序运行。

建立使用相同数据、工具和约束的单 Agent 对照配置，与专业协作在相同案例和可比预算下比较。记录可执行方案率、协调质量、延迟和实际 token；协作的默认启用以评估收益为依据。该对照用于验证架构价值，不要求先删除或合并现有专业模块。
